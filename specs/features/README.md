# Feature specifications

One file per feature. A feature spec describes **desired behaviour**, not the current implementation. It may overhaul or override current behaviour if that is what the product needs.

## Start a new spec

1. Copy [TEMPLATE.md](TEMPLATE.md).
2. Name it `F-NNN-<feature-name>.md` using the next free number in [INDEX.md](INDEX.md); the slug is the user-facing feature name, not the module or an internal pair of concepts.
3. Add a row to the index with status `Draft`.
4. Fill in the template; keep rule IDs and acceptance-criteria IDs stable.
5. When ready, move it to `In review` and ask for critique/vetting.
6. Only after acceptance should implementation begin.

## Ownership and agent rules

Feature specs are owned by the product owner, not generated by agents.

- An agent may scaffold a spec, ask clarifying questions, check consistency with other docs, and edit wording on request.
- An agent must not invent feature behaviour, defaults, priorities, rules or acceptance criteria unless explicitly instructed.
- When an agent drafts anything normative, label it. Use a `Source` column (`baseline`, `proposal`, `owner`) or an explicit note. Nothing is a requirement until the owner marks it `owner`.
- A file described as an **empty scaffold** is intentionally empty: leave its feature sections untouched.
- When resuming in a new session, read [specs/README.md](../README.md), this file and the [assessment](../../docs/codebase-assessment.md), then ask the owner for the first decision.

## What belongs here

- User problems, goals and non-goals.
- User flows, including empty, loading, error and offline states.
- Functional rules and edge cases.
- Data the user sees or edits, and validation rules.
- API behaviour that is part of the feature contract.
- Acceptance criteria and test expectations.
- Privacy, security and accessibility requirements specific to the feature.
- Compatibility and migration notes when current behaviour changes.

## What does not belong here

- Internal package layout, framework choice or class design — use the architecture spec.
- Raw evidence about the current code — link to [the assessment](../../docs/codebase-assessment.md).
- Vague aspirations without testable criteria.
- Duplicated copies of global conventions.

## Writing style

- Use the user’s language for user-facing behaviour; use precise domain terms for rules.
- Number functional rules (`FR-1`, `FR-2`) and acceptance criteria (`AC-1`, `AC-2`).
- State defaults and precedence explicitly.
- Describe what happens when a dependency is unavailable.
- Mark decisions that are still open with `OPEN:` and resolve or defer them before acceptance.

## Baseline

The current implementation is documented in [docs/codebase-assessment.md](../../docs/codebase-assessment.md). It is a source of evidence and behaviour to preserve, not a constraint on the future product.

If a spec overrides current behaviour, include:

```md
## Compatibility and migration

- **Breaking:** yes
- **What changes:** ...
- **Existing data:** ...
- **Migration:** ...
- **Rollback:** ...
```
